# Brancher une IA à l'application

Spécification fonctionnelle, rédigée le 25/11 (demande du 24/11). Ce document se lit seul.

## 1. Besoin

Aujourd'hui, les outils de l'application (chercher, étiquettes, cahier de recherche, etc.) ne sont donnés qu'à la colonne Claude Code, le temps d'un tour. L'utilisateur veut s'en servir depuis une IA extérieure à l'application, par exemple l'extension Claude de VS Code ou Codex, sans ouvrir aucun port réseau.

## 2. Vocabulaire

- **Brancher une IA** : donner à une IA extérieure l'accès aux outils de l'application.
- **Clé de branchement** : le secret que l'IA présente pour être écoutée. Elle est stable : elle ne change que si l'utilisateur la révoque. À ne pas confondre avec la clé du tour, propre à la colonne Claude Code.
- **Commande de branchement** : la petite commande que l'IA lance pour joindre l'application (le programme de l'application lui-même, comme le relais de la colonne Claude Code).

## 3. Comportement

- Un onglet **« Brancher une IA »** dans les Réglages. Tout s'y fait avec des boutons.
- **Sans clé** : l'onglet explique en une phrase à quoi il sert et montre un seul bouton, **« Créer une clé de branchement »**. Tant qu'il n'y a pas de clé, l'application n'ouvre aucune prise pour les IA extérieures.
- **Créer** : le bouton crée la clé et l'affiche avec un bouton **« Copier »**. Dessous, deux blocs de configuration prêts à coller, chacun avec son bouton « Copier » :
  - pour **Claude** (extension VS Code et Claude Code hors de l'application) ;
  - pour **Codex**.
  Chaque bloc contient la commande de branchement et la clé ; il n'y a rien d'autre à chercher ni à taper.
- **Où coller chaque bloc** : sous le titre de chaque bloc, une phrase dit dans quel fichier le coller, avec le nom du fichier en style code :
  - Claude : « Collez ce bloc tel quel dans le fichier `.mcp.json`, à la racine du dossier ouvert dans l'éditeur. Si le fichier existe déjà, ajoutez l'entrée du bloc dans « mcpServers ». » (`.mcp.json` est le fichier des serveurs MCP d'un projet pour Claude Code et son extension VS Code) ;
  - Codex : « Collez ce bloc tel quel à la fin du fichier `~/.codex/config.toml`. » (le fichier de configuration de Codex, où chaque serveur MCP est une section `[mcp_servers.<nom>]`, ce que le bloc est déjà : du TOML valide).
  La clé seule n'a pas de phrase. Les phrases se lisent en thème clair et sombre et ne font jamais déborder la fenêtre des Réglages, dont la taille reste fixe (le contenu défile).
- **Le fichier `.mcp.json` ne se commite pas** : il contient la clé de branchement ; le dépôt du projet l'ignore (`.gitignore`).
- **Avec une clé** : l'onglet montre qu'elle existe, la date de sa création, les blocs à copier et un bouton **« Révoquer la clé »**. La clé reste affichée et copiable tant qu'elle existe.
- **Révoquer** : le bouton, après confirmation, efface la clé. Les IA déjà branchées sont coupées tout de suite et l'application referme la prise. Le bouton « Créer une clé de branchement » revient ; une nouvelle clé n'a rien à voir avec l'ancienne.
- **L'application doit tourner** : l'IA extérieure n'est écoutée que tant que l'application est ouverte. Fermée, la commande de branchement répond à l'IA que l'application n'est pas lancée.
- **Ce que l'IA reçoit** : les mêmes outils que la colonne Claude Code, sur les espaces de travail que l'utilisateur a autorisés, désignés par leur nom et jamais par un chemin. Les règles de l'application s'appliquent à l'identique (corbeille, dossier des pièces jointes, cahiers en ajout seul).
- **Choisir les espaces de travail** : sous le texte d'introduction, l'onglet montre la liste des espaces de travail de l'utilisateur, **une case à cocher chacun** (« Espaces de travail ouverts aux IA »), avec ou sans clé. **Aucune n'est cochée au départ** : une IA branchée ne voit alors aucun espace. Cocher un espace le rend visible et utilisable par les IA ; le décocher le leur retire tout de suite. L'état se garde d'un lancement à l'autre, avec les préférences de l'application (jamais dans l'espace de travail) ; créer ou révoquer la clé ne le change pas. Les réglages de l'application (thème, largeur du texte…) ne sont jamais ouverts à une IA.
- **Lister les espaces** : l'outil `list_workspaces` donne à l'IA le nom de chaque espace coché, avec celui qui est ouvert chez l'utilisateur ; aucun coché : une liste vide et un message qui renvoie à l'onglet « Brancher une IA ».
- **Choisir l'espace d'un outil** : chaque outil accepte un paramètre facultatif `workspace` (un nom). Sans lui, c'est l'espace ouvert chez l'utilisateur, s'il est coché. Un nom inconnu ou non coché est refusé, avec la liste des noms permis. L'espace choisi s'ouvre en arrière-plan : l'écran et l'espace de l'utilisateur ne changent pas. Un espace décoché ou disparu pendant le travail refuse l'appel suivant, sans rien écrire ailleurs. `viewed_note` et `show_note`, qui parlent de l'écran, ne visent que l'espace ouvert.
- **Lire le texte d'une note** : l'outil `read_note` rend le texte entier d'une note simple, avec son en-tête (les propriétés, telles qu'elles sont écrites) à part du corps, de sorte que l'IA puisse recopier à l'identique le texte à remplacer pour `replace_in_note`. Jusqu'à 60 000 caractères de corps ; une note plus longue est coupée à la fin d'une ligne et la réponse le dit (jamais de coupure silencieuse). Refusé, avec une phrase qui dit quoi faire, sur un cahier de recherche (on n'y ajoute que des entrées, par `add_entry`), une carte mentale, un canvas (`read_canvas`) et un CRM ou ses fiches (`read_crm`), ainsi que sur une note introuvable ou hors de l'espace. Fiche 0076.
- **Les modèles de note** : `list_templates` donne les noms des modèles de l'espace visé et `create_note_from_template` crée une note depuis l'un d'eux, avec le dossier des modèles que l'utilisateur a choisi dans les Réglages pour cet espace (il est gardé avec l'espace dans les préférences de l'application, un seul endroit pour l'interface, les IA et la colonne Claude Code). L'IA ne voit ni ne choisit ce dossier ; sans dossier choisi pour l'espace visé, l'outil le dit avec le nom de l'espace. Fiche 0077.
- **Changer le texte d'une note** : l'outil `replace_in_note` remplace un texte par un autre (`old_text`, `new_text`) dans une note simple, avec les règles de la saisie (version du texte d'avant gardée, index à jour, nom du fichier qui suit le titre). Le texte à remplacer est recopié à l'identique (il se lit avec `read_note`) ; s'il est introuvable, vide ou répété, l'IA reçoit une erreur claire en français et rien n'est changé ; `replace_all` à vrai remplace toutes les occurrences. Refusé sur un cahier de recherche (on n'y ajoute que des entrées, par `add_entry`) et sur une carte mentale, un canvas (outils du canvas) ou un CRM (outils du CRM). Fiche 0075.
- **Les dossiers** : `list_folders` donne l'arbre des dossiers de l'espace visé (chemins depuis sa racine, dans l'ordre de l'arbre de l'interface ; ni dossiers cachés, ni `.assets`, ni `node_modules`, ni corbeille) ; `create_folder` crée un dossier (et ceux qui manquent sur son chemin) ; `rename_folder` (`path`, `name`) et `move_folder` (`path`, `folder`) renomment et déplacent un dossier avec tout son contenu ; `trash_folder` (`path`) le met à la corbeille avec son contenu, sans jamais l'effacer. Ils passent par les mêmes cas d'usage que l'interface : mêmes noms refusés (vide, caché, terminé par `.assets`, `node_modules`, caractères interdits), mêmes messages en français, la racine intouchable, un dossier jamais dans lui-même. Notes, pièces jointes, historique et index suivent ; les liens `[[Dossier/titre]]` ne sont pas réécrits, comme dans l'interface. Fiche 0078.
- **Le canvas** : `read_canvas` rend un canvas comme des données (cartes avec identifiant, type, position, taille, couleur de la palette, texte, fichier ou adresse ; flèches avec leurs deux cartes, côtés, sens et étiquette ; groupes avec leurs cartes ; étiquettes), jamais le JSON brut, borné à 150 cartes, 150 flèches et 20 000 caractères de texte avec un message de coupure quand il faut. Dix outils le changent, un par geste de l'interface : `add_canvas_card` (texte, fichier ou page web), `change_canvas_card` (texte, adresse, fichier, couleur), `move_canvas_card` (les cartes d'un groupe suivent), `resize_canvas_card`, `remove_canvas_card` (les flèches qui y touchent partent), `add_canvas_arrow`, `change_canvas_arrow` (sens, étiquette, couleur, extrémités), `remove_canvas_arrow`, `add_canvas_group` (vide ou autour de cartes) et `change_canvas_group` (nom, couleur). Mêmes règles que l'interface : couleurs de la palette de l'application seulement (`aucune` pour en retirer), identifiants stables, propriétés inconnues conservées, version d'avant gardée dans l'historique (un changement d'IA s'annule avec `restore_version`), index à jour, fusion si le fichier a changé entre-temps ; l'écran ouvert suit. `add_tags` et `remove_tags` écrivent `tags` à la racine d'un canvas. Fiche 0079.
- **Le CRM** : `read_crm` rend un CRM comme des données (colonnes du Kanban avec leurs actions, urgences, personnes avec leur entreprise du moment, entreprises, projets avec leur couleur et leurs étiquettes, étapes, compteurs), avec les filtres de l'interface (mot cherché, personne, entreprise ou NODATA, projets, étiquettes), jamais les fichiers des fiches, borné à 100 actions, 100 personnes, 100 entreprises, 100 projets et 20 000 caractères de textes libres avec un message de coupure quand il faut. Quatorze outils le changent, avec les règles de l'interface (mêmes messages en français) : créer, changer et supprimer une action, une personne, une entreprise ou un projet (`create_crm_action`, `change_crm_action`, `delete_crm_action`, `create_crm_person`… ; le changement d'une fiche prend une `operation` qui nomme le geste de l'interface : titre, date, canal, projet, couleur, notes liées, personnes, description, listes à cocher et leurs éléments, commentaires pour une action ; nom, champ, notes, changement d'entreprise pour une personne ; nom, champ, notes pour une entreprise ; nom, couleur pour un projet), déplacer une action dans une colonne du Kanban (`move_crm_action` : statut et place), changer les étapes (`change_crm_stages`). Une fiche se désigne par sa référence (`ref`, rendue par `read_crm`) ; une suppression va à la corbeille et nettoie les fiches qui la nomment ; les étiquettes d'une fiche se changent avec `add_tags` et `remove_tags`. Un CRM se désigne par son chemin (`search_notes` avec le type `crm` les liste). Fiche 0081.
- **La colonne Claude Code** : son espace de travail reste celui du tour, coché ou non ; elle peut viser un autre espace coché par `workspace`, comme une IA branchée.
- **Sans clé ou avec une mauvaise clé** : tout est refusé.

## 4. Contraintes

- **Aucun port réseau** : ni TCP, ni UDP, ni écoute sur `localhost`. Seule une prise locale du Mac sert, dans un dossier que seul le compte de l'utilisateur peut ouvrir (voir la fiche 0040).
- **Stockage de la clé** : un fichier lisible par l'utilisateur seul, hors de l'espace de travail et jamais dans les notes. Elle n'est ni écrite dans un journal ni envoyée nulle part.
- **Risque assumé** : un programme du Mac qui connaît la clé lit et écrit les notes comme l'IA branchée. C'est pourquoi la clé est révocable en un clic.
- **Les mêmes outils pour tous** : la colonne Claude Code et les IA extérieures partagent un seul serveur d'outils ; un outil ajouté sert aux deux.

## 5. Hors de cette version

- Plusieurs clés distinctes (une par IA), avec un nom chacune.
- Choisir les outils permis à chaque IA.
- Un mode réseau ou l'API ouverte à d'autres IA (tâche à part).

## 6. Vérification avec les vrais outils

L'essai se fait avec l'extension VS Code et avec Codex, sur le vrai `.app`. L'utilisateur est prévenu avant que la fonction soit annoncée terminée, avec les gestes exacts à essayer.
